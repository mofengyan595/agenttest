## AgentTest增加了什么

首次审核项目后，现有目标目录把受支持的原文映射到批准操作、角色、资源关系和状态。
用户不需要逐题写完整步骤、资源偏序或TaskContract；CLI、任务服务和工作台共用执行路径，
展示未执行原因并导出通过的固定场景。这是可用入口和工程机制的证据；是否更方便仍需真实使用者验证。

模型提出合法基线并可提出诊断建议；规则负责目标约束、门禁、变体、预算、可信断言和证据结论。
同一结构派生十个场景不会变成十次模型规划成功，安全待审也不等于测试完成。
基础计划失败仍会阻断整组派生，模型诊断仍须和实际证据核对。

现有离线CatalogFixturePlanner也能从公开批准关系和默认输入组装这些已知结构，
因此Mock门禁证明的是受支持路径可运行，不能证明LLM在这些目录内不可替代。
本轮没有建立“真实模型优于完全确定性组装器”的证据，也没有把Mock规划器接成线上失败回退。

新的六任务与三轮结果是开发对照，既有业务结构和固定baseline→candidate顺序限制了泛化和因果解释。
只有相同覆盖、相同任务轮次均完整完成的位置，才可用于检验等成功覆盖的调用/Token差异；
整体调用总数必须同时看实际覆盖，不能用“少测了”证明效率。

真实旧版2/18、候选9/18完整；候选足额9/15、项目3/6、批准负例85/105，三项质量目标未达。
候选103个实际派生全部经原门禁并执行，但预定129中另26个被失败基线阻断。
总调用162→50、Token239098→80838是同一覆盖要求下的描述性成本；只有一对等完整配对，
3→2调用来自流程反馈少一次可选调查，该流程没有派生，不能宣称计划复用的独立因果节约。
共同子集固定84/84、候选76/84且另需12次模型；已知检查没有显示模型额外质量优势。
Agent子集来自64请求完整任务的预先指定提取，实际均未超工具8/6/9上限，未单独强制子集预算；
因此不把附表当作独立同预算四组实验。阶段1严格三组9请求对照仅为模拟。

## 准备和运行成本

| 路径 | 需要维护的内容 | 未验证部分 |
|---|---|---|
| 共同基础 | 契约、隔离地址/操作、角色凭据、可信错误与业务预期、重置条件 | 审核耗时未计时 |
| 固定用例 | 三项目手写fixture、登录/创建步骤、合法输入与断言；稳定后不调用模型 | 新需求手工编写耗时未计时 |
| Schemathesis适配 | 独立依赖锁、公开Schema与批准字面量交集、受控生成设置、原执行器适配 | 原生状态探索未比较，表示兼容仍有限制 |
| AgentTest | 上述基础加目标词汇、资源/状态关系、预算与模型配置；支持范围内新增需求只给原文 | 模型调用、Token和机器耗时见真实结果；没有人工收益证据 |

三项目共用公开批准配置，比较不能隐藏这部分人工作业。独立Schemathesis环境未加入产品运行依赖，
主离线路径仍不需要模型、Docker或网络。没有价格/账单依据，不将Token换算成虚构货币费用。

本轮继续采用已有确定性派生，保留Schemathesis为可选独立对照。稳定已知测试交给固定资产，
契约生成与更宽探索可使用成熟工具；Agent主要承担受限业务规划和待证据核对的诊断建议。
