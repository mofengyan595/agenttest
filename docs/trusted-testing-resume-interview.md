# 可信测试增量：简历与面试材料

定位仍是辅助展示Agent工程能力的独立Python项目，不替代Java后端项目中的数据库、并发和服务治理证据。
以下只描述已完成的机制；真实排期12/36、足额12/30、足额项目0/6，质量目标未达到，
不写“规划成功率80%”“完整项目稳定完成”或“任意项目零配置”。

## 简历条目

- 在现有API测试平台中实现批准负例执行：模型引用项目级策略，确定性执行器构造必填缺失、类型、枚举和边界变异；正常请求保持完整校验，负例只允许命中明确批准的违例，并使用可信错误断言区分正确拒绝与目标缺陷。
- 实现项目级测试分组、当前组公开目录裁剪及父子共享预算，预览必需请求、可执行组和排除原因；分别记录候选、合法计划、实际执行与断言分母，避免将部分通过报告为完整项目完成。
- 在课程、工单和实验室专用合成目标复用同一执行引擎，验证双生产者资源依赖与角色约束；提供正常/负例的无模型pytest回归、可追溯GoalSpec待审草案及现有React工作台的预算/负例展示，保留冻结排期和失败证据。

第三条包含开发者Fake/Mock和真实模型对自建ASGI目标的验证，不是独立项目留出或泛化结论。第三项目原Fake记录为20场景、36 ASGI请求、
15批准负例；新增需求无需逐题手写步骤，但首次接入仍审核契约、角色、策略、资源关系、错误预期和预算。

## 面试案例一：为什么不能直接放开非法输入

问题：Schema可以生成非法值，却不能证明错误响应的业务语义；原执行器也会在发送前正确阻止它们。

失败场景：想验证“少一个必填字段时返回批准错误”，请求却在本地验证阶段终止。直接skip_validation会让
其他字段、资源ID、凭据和地址失去保护，甚至把任意错误请求算成负例成功。

方案：像先检查一件合格样品，再只改质检单点名的字段。项目策略固定基线、字段、变异和可信错误响应；
模型只引用批准能力，执行器先验证完整基线，再校验变异恰好产生批准的违例集合。

替代方案取舍：不用全局跳过校验，不由模型提交任意非法值，不从OpenAPI猜具体错误码，不修改断言追求PASS。

实现与验证：negative.py、Policy、DSL、Executor、Verifier和固定导出模板协作；类型同时违反枚举时必须双重批准。
专用目标覆盖正确拒绝、错误接受、错误正文、未批准变异阻断，正常/负例固定回归在模型禁用时执行。
目前只覆盖现有Schema子集和已审查单字段body/query变异；路径、凭据、文件和未知错误语义不能套用。

## 面试案例二：为什么项目“通过了几个”仍可能没完成

问题：模型常把项目目录当成执行清单，多加或漏掉步骤；每组单独用预算也容易挤占后续组额度。

失败场景：旧归档保存了STEP_COUNT/STEP_SET、额外步骤和预算排除；局部PASS不代表完整项目已测完。

方案：批准关系先决定组与覆盖分母，每次只给当前组需要的接口、角色和资源关系。模型提出计划，
原门禁检查遗漏、额外操作、参数来源、角色、状态和顺序；共享ledger预留后续业务请求与规划槽位。

替代方案取舍：不静默补步骤、重排计划或替换策略，不把逐题标准计划给模型，也不扩大预算后重算旧成绩。

实现与验证：goal_suite.py和GoalPlanner复用原Workflow，测试足额完成与不足安全退出。
报告同时保存候选、提案、合法计划、执行、断言及未执行。原6031212 Mock排期还暴露了输入估算超限，
说明“请求预算足够”不等于“所有模型输入能装下”，需要如实保留预算失败。
