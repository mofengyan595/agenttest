# 组合规划约束修复与验证（2026-10-14）

本里程碑处理[真实补验](real-model-coverage-20261014.md)暴露的组合约束表达缺口，并补充安全诊断。原十六条任务的首次成绩、两个封印归档及未执行记录不覆盖；原始模型回复没有保存，不能事后追溯五条旧结构失败的具体生成值。

## 修改范围

组合草稿原来分别列出 Operation、Policy、Role、CSV 和 Poll 的枚举，但 JSON Schema 没有表达它们之间的组合关系。现在只在 `mini_composed` profile 中，从同一完整批准目录生成七类 `step_options`，并写入步骤 Schema 的 `anyOf` 分支：

- 操作与策略必须匹配，角色范围与可见目录取交集。
- 批处理三种操作仍只允许 alice；工单通用入口和原独立 batch profile 不变。
- 只有上传步骤必须选择批准的 CSV 引用，其他步骤该字段为 null。
- 只有状态轮询步骤必须选择批准的 Poll 引用，结果读取该字段为 null。

该投影与任务文本无关，不从标签生成步骤，不提供完整标准路径，也不增加策略权限。空候选目录在模型请求前拒绝。Policy／DSL／Intent 继续核验登录顺序、同一资源传递、参数及完整目标；服务符合 JSON Schema 也不能替代本地授权。

原提示中的“不要增加登录”改为“只添加被选保护操作所需的登录”：每个选定角色按输入中的 authentication 在其首个保护操作前登录，即使任务未提到登录，也必须满足已有前置条件。没有自动插入登录、排序步骤、修复引用或重规划。

跨字段校验仍拒绝同样的非法计划，错误改为四类闭合代码：`MODEL_SCHEMA_COMPOSED_POLICY_MISMATCH`、`MODEL_SCHEMA_COMPOSED_ROLE_UNAPPROVED`、`MODEL_SCHEMA_COMPOSED_CSV_REFERENCE`、`MODEL_SCHEMA_COMPOSED_POLL_REFERENCE`。诊断只保存代码和安全字段路径，不保存原始回复、生成值或异常上下文。

[学校结构化输出文档](https://developer.ecnu.edu.cn/vitepress/llm/api/structuredoutput.html)要求用 JSON Schema 描述结构，提供约束解码。本阶段没有更换协议或服务，仍使用现有 HTTPX 适配器；具体分支结构是否被该服务接受，以本次真实调用为准，不降级为自由文本或自动回退。

## 已完成的离线验证

新增七项回归在修复前全部失败，修复后全部通过。其中一个矩阵检查穷举 336 种 Operation／Policy／Role／CSV／Poll 搭配，确认发出的 Schema 与本地步骤校验完全一致，批准组合有 11 种角色展开形式。其他检查验证错误分类无生成值泄漏、可见角色／策略范围、空目录零调用，以及服务返回非法结构时不修复、不重试。

扩大相关回归 **267 passed / 289.85s**，覆盖原组合、batch、模型适配、公共诊断、审核和通用迁移入口；Ruff 通过。Windows 沙箱内最小事件循环探针阻塞，终止自己的阻塞进程后，在沙箱外运行离线测试，既有禁网夹具和 MockTransport 保留。没有关闭安全检查。

六条新任务的显式固定响应验收：四条正常路径完成、两条模型弃权，零真实模型调用；900 Token 为 SIMULATED，不能描述为真实消耗。两种离线证据都不能证明修复后的真实规划成功率。未重跑全量 Python、Web、Java 或远端 CI。

## 新任务与真实验证方案

[P101–P106 开发任务](../examples/composed-constraints-development.json)包含批处理、读取与批处理组合、三目标文本换序、bob 创建者权限，以及未批准角色批处理和未支持删除。它们的文本与此前十二题不同且未调用过模型，但业务语义与旧题同族，标签由 AI 起草，**不是独立留出集**。只作一次开发回归，不做统计意义的前后 A/B。

沿用用户已授权的真实验证范围，使用同一学校 ecnu-plus、原适配器和进程内隔离目标。最多六次、每题一次、不重试；每次输入上限 20,000、输出上限 4,096 Token，累计保留上限 144,576。输入包含合成任务和批准目录／Schema，没有标准计划、标签、凭据、真实业务记录或 CourseInsight 源码。Java、生产请求和真实数据库写入仍为零。

开发诊断使用原私人运行器，仅换新任务来源；未知 usage 或服务错误停止，已知 usage 的结构失败保留后只继续其他未执行题。正式评测入口的独立审核与干净提交门禁不变。

### 首批真实调用结果（30 秒上限）

冻结方案、源码身份和六份准确出站请求核对后，P101 实际调用一次，在 30 秒模型超时处结束：`TEST_INFRA_ERROR / MODEL_TIMEOUT`，没有 HTTP 状态、回复或 usage，零业务请求。预算保留 24,096，不返还或把未知消耗记为零；停止原因 `MODEL_USAGE_UNAVAILABLE`。本批 P102–P106 保留为未执行，不恢复已停止目录、不重试 P101。归档冷校验与六行完整分母重新评分通过。用户随后要求继续验证，剩余题另行冻结，见下节。

随后只做一次 `GET /models` 元数据检查，HTTP 200、配置模型存在、generation_calls=0；认证和服务入口可用，但它不能证明生成接口延迟、该分支 Schema 被服务接受或修复后的规划效果。旧一轮末尾也有超时；目前没有足够证据将本次超时归因于服务负载、约束编译或输入复杂度。

P101 请求为 15,908 字节，保守输入 Token 上界 16,420，未超 20,000 的输入预算；已发送的跨字段分支增加了请求长度，不能宣称 Token 或费用降低。实际消耗未知。首批没有取得可用于判断计划成功或失败的模型回复，不计 0/4 正常任务成功率或 0/2 拒绝率来混淆未执行题。

### 续批真实验证（60 秒上限）

用户要求“验证一下”后，先核对 45 份交付文件摘要，全部与上次验收一致。只在新的私人验证运行器中将模型等待改为 60 秒、Workflow 规划等待 65 秒、整链等待 120 秒；用固定响应确认实际预算生效且五题归档能重新评分。项目功能代码、提示、断言及原 `ModelSettings` 默认 30 秒未修改。

只调用 P102–P106，各一次，上限五次／保留 120,480 Token。与首批保留 24,096 合计仍为六次／144,576；P101 的未知消耗不返还，不重试。五份准确出站消息与原核对内容逐字节一致，只有等待配置与冻结源码中的文档记录不同，没有补标准步骤、调整标签或接入真实业务系统。

P103 的脱敏计划证据明确显示：模型先安排 bob 的拒绝读取，后安排 alice 的成功读取。本地 DSL 与 Policy 均通过，Intent 报 `ORDER_MISMATCH:read:denied`，在任何业务请求前拒绝。这证明当前问题仍包括跨步骤业务偏序，单步结构约束不能解决完整计划排序。P105 的计划也没有主动弃权；P106 的部分计划被意图检查拦住。这些失败原样保留，不自动排序或追认 PASS。

续批已知 usage 合计 **13,935 Token**。两批六题合并：2 PASS、3 NEEDS_REVIEW、1 TEST_INFRA_ERROR；没有未调用题或重复调用，成功任务共 12 次进程内业务请求，其他任务全部零业务请求。P101 用量未知，因此两批累计实际 Token 保持 null，不能把 13,935 当完整账单。

续批封印冷校验及五题重新评分通过；首批仍保留六行原记录，其中五行未执行。`combined-verification.json` 从两个原始归档按已尝试任务去重核账，确认六次调用及预算上限，未覆盖旧档。两次模型规划超过 30 秒，说明较长等待在本次验证有实际作用；不能从不同任务推断 P101 超时的唯一原因，也不能宣称原默认等待已完成相同验收。

结论：读取＋批处理及角色互换取得真实成功证据，**三目标排序和模型主动拒绝仍未修好**。下一准确里程碑是显式表达可信跨步骤偏序，并在新的未用任务上验证排序与拒绝行为，保留本轮失败，不继续围绕这六题改提示调分。陌生第三方项目、独立留出集及生产可靠性仍未覆盖。
