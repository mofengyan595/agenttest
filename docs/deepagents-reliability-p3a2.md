# P3-A.2 自主测试可靠性与自适应执行预算

起点为 P3-A.1 的 `52779c9652f76a65981256e38e6e04de5783ed23`（本分支 `0bf18fb`）。运行时不变：Deep Agents 0.7.35 单一主 Agent、LangChain 1.4.10 / LangChain Core 1.7.7、LangGraph 1.2.20、Python 3.11。本轮没有新增第二个 Agent 循环、没有可执行模型代码、没有放宽批准与断言校验。

## 1. 原始问题与根因

四类问题在 P3-A.1 的真实运行里各有可核对的现场。

### 1.1 Focus 与范围不可比

- `.eduwork/runs/p3a1/final-v2/functional/run.json` 报“范围 6/6 义务全部有执行证据”，同一份报告里 Focus 把 `readAvailability` 排除在外，而项目已批准义务是 31 项。分母随 Focus 收缩而收缩，于是“测了 6 项”和“测了 6/31 项”在报告上长得一样。
- 删除回归 Focus 只映射了删除，创建前置缺失，报告仍以 1/1 呈现“范围完成”。
- 上线前把 24 项批准负向义务排除在完成判据外，报告没有说明这 24 项去了哪里。

根因不是某一行代码算错，而是**只有一个覆盖数字**：请求范围、批准范围、Focus 选中范围、实际执行范围从来没有分开记录，所以任何一次分母收缩都只能是隐形的。

### 1.2 负向 POST 与资源生命周期

- `.eduwork/runs/p3a1/final-v2/prerelease/run.json` 中一次获批负向 POST 得到预期的 422，账本按“执行过的 POST”计为创建，完成判据因“资源未清理”判未完成，但没有创建凭据可绑定。
- 反方向同样有害：`204` 删除回执被当成清理成功，未回读；一旦靶场“删了但没删掉”，就会被记成已清理。
- P2 曾在上线前目标泄漏 10 个包裹，正因为“没有凭据”和“没有副作用”被混为一谈。

根因是**把状态码当成副作用结论**：422 不等于没创建，`record_count=0` 不等于没创建，`204` 不等于已删除，模型说“已清理”更不构成证据。

### 1.3 统一的低调用上限

P3-A.1 的每任务上限是 16 次模型调用、30 次业务 HTTP、420 秒，三个数字对所有目标一视同仁：

- 功能 8 次调用就完成，预算有 8 次剩着；
- 删除回归用满 16 次仍被截断；
- 上线前 31 项批准义务（7 正 + 24 负）在 30 次请求里根本装不下，估算从未做过。

上限没有来源、没有范围、没有停止理由，也不参与“是否还有真实进展”的判断，于是**合法任务会因为统一的低上限提前放弃**。

### 1.4 把“调查完成”当成“接口测完”

调查目标把一次 `investigate_failure` 的成功当成整个 API 被测过，报告里不区分“解释了一个现象”和“覆盖了批准义务”。

## 2. 实际改动与被替换的机制

| 机制 | 之前 | 现在 | 位置 |
| --- | --- | --- | --- |
| 执行预算 | 16 / 30 / 420 三个常量，全目标统一 | `ExecutionBudget`：模型调用、Token、Agent 轮次、工具调用、业务 HTTP、时间、组运行、义务运行八个维度，每个都有基数、天花板与来源；`FIXED`/`ADAPTIVE` 两种模式 | `src/agenttest/execution_budget.py` |
| 预算估算 | 无 | 由 Planning IR、批准策略、依赖图与生命周期推导请求区间与模型调用区间，输出区间与依据，不声称精确值 | `estimate_round()` |
| 预算增长 | 无 | 只在观察到真实进展后增长：新合法计划、新可信证据、义务覆盖增加、阻塞解除、清理完成；HTTP 授权永不增长 | `ExecutionState.observe/extend` |
| 停滞检测 | 无（只有硬性截断） | 确定性的无进展计数（默认 3 次），无新 LLM 看门狗 | `progress_signature/progress_delta` |
| 覆盖口径 | 单一数字 | 四份范围账本：原始请求、已批准范围、Focus 选中范围、实际执行范围，附差异原因与可比比率 | `src/agenttest/scope_ledger.py` |
| 写副作用 | “执行过的 POST 就是资源” | 六态判定：已创建已清理 / 证明无副作用 / 创建未证实 / 创建但清理失败 / 清理未证实 / 写入结果未知 | `src/agenttest/write_effects.py` |
| Focus 纠错 | 一次拒绝即中断或静默改范围 | 有界纠错：把结构化错误喂回一次（含解码失败），仍不合法则 `NEEDS_REVIEW`；授权冲突类错误不重试 | `product_tasks.py`、`request_requirements.py`、`product_focus.py` |
| 用例标识 | 同一组重复执行会写两条同名记录 | `unique_case_id()`：重试的组获得独立用例号，资源账本按行计数 | `product_tasks.py` |

同时修正了四处“源常量式”限制：

- `TargetConfig.run_timeout` 与 intake 的 `run_timeout` 上限原本是 300 秒，P3-A.1 的 420 秒只能靠消融脚本旁路注入，无法作为正式配置传递。本轮放宽到 3,600 秒，让长轮次成为可配置、可审计的字段；超过一小时仍被拒绝（回归用例同时断言 3,601 秒被拒）。
- `ModelSettings.max_input_tokens` / `max_total_tokens` 与 `ProjectBudget.max_input_tokens` 的上限放宽到模型真实窗口与运行天花板。上线前设计请求曾在 20k 字节信封处被 `MODEL_TOKEN_BUDGET` 拒绝、零派发，这是“源头常量”问题：ADAPTIVE 让信封随模型窗口，FIXED 保持历史信封以便 A/B 复现。
- 工具异常补了证据通道：每个任务最多记录 8 条 `tool_errors`（工具名、错误、截断 traceback），只进证据、不进模型上下文。
- 预算与天花板成为 `ProjectBudget` 的正式字段（`execution`），默认值不写进历史工程文件，保证旧工程读回后字节一致。

## 3. Focus 与覆盖口径

`agenttest.scope-ledger.v1` 同时记录四个范围：

- **requested**：原始需求文本经确定性主体闭包得到的已批准义务；包含 `resolved`、主体词元、操作列表与未获批准的部分。
- **approved**：项目全部已批准义务（`design_groups` 全量展开），与请求无关，作为固定分母。
- **selected**：本轮 Focus 真正选中的义务，并对“读/删某资源标识”的义务补齐其唯一已批准生产者（与 IR 编译器的前置投影一致）。
- **executed**：带真实执行证据的义务。

差异逐条给出原因：`NOT_IN_REQUESTED_SCOPE`、`FOCUS_BLOCKED`、`OPERATION_NOT_READY`、`REQUESTED_BUT_NOT_SELECTED`、`SIBLING_OPERATION_NOT_SELECTED`、`FOCUS_ADDED_PREREQUISITE`、`NEGATIVE_VARIANT_NOT_SELECTED`。

- `REQUESTED_BUT_NOT_SELECTED`（需求点名、却没进选中范围、也没有别的理由）会让完成判据失败——这正是 P3-A.1 里“删除回归漏掉创建前置”的形态。
- `SIBLING_OPERATION_NOT_SELECTED` 是这一轮新增的区分：回归/调查目标说的是一个行为（“删除功能刚改过”），确定性主体闭包却会列出该资源下所有已批准策略。原文没点名的兄弟操作（PATCH/PUT）不算静默收窄；原文点名的那一项仍受 `SUBJECT_OBLIGATIONS_MEASURED` 与“已批准生产者前置”审计约束，收窄不会被放过。
- `NEGATIVE_VARIANT_NOT_SELECTED` 记录“功能/回归目标不跑全部非法取值，上线前才跑”这一目标类型差异，既不隐形也不阻塞。

完成判据新增两行：

- `APPROVED_SCOPE_COVERAGE`（信息行，`EXEMPT`）：公开“选中 6/6、批准 6/31、另有 24 项已批准义务不在本轮选中范围”。
- `REQUESTED_SCOPE_SELECTED`：原文点名的操作是否都进入选中范围；主体未解析时为 `EXEMPT`。

因此“调查完成”不再等于“接口测完”：调查目标只覆盖被调查主体，报告同时公开它对批准范围的覆盖比例（本轮调查目标实测“选中 6/30、批准 7/31”）。

## 4. 负向 POST 与资源生命周期的证据

`agenttest.write-effects` 只在**创建型写**上判定（有生命周期行的步骤，或无路径参数的集合 POST）；`PUT`/`PATCH` 是对已存在资源的属性变更，`DELETE` 由自己的回读判定，都不再被算成“新资源”。

| 状态 | 判定依据 | 是否算已解决 |
| --- | --- | --- |
| `CREATED_AND_CLEANED` | 有绑定标识 + 批准删除回执 + 同一资源的批准缺失回读（404/410） | 是 |
| `NO_SIDE_EFFECT_PROVEN` | 被拒（4xx/预检拒绝）+ 批准回读证明目标状态未变 | 是 |
| `CREATION_UNPROVEN` | 被拒但无批准回读，或创建成功但无可绑定标识 | 否，保留待人工核实 |
| `CREATED_CLEANUP_FAILED` | 有绑定标识，批准清理执行过但失败 | 否 |
| `CLEANUP_UNPROVEN` | 有绑定标识但没跑清理；或删了但没回读（`204` 不算证明） | 否 |
| `WRITE_OUTCOME_UNKNOWN` | 请求已发出但没有可用结果（超时/断连） | 否，且禁止重放 |

关键取舍：**没有批准回读就不许推断“无副作用”**。冻结靶场没有集合列表读，也没有为“被拒集合 POST”批准缺失读，所以 422 之后的副作用无法在不扩大授权的前提下证明：状态保留 `CREATION_UNPROVEN`，并附结构化诊断（需要在批准策略里补一条缺失读或列表读）。本轮边界目标 r3 的 12 条 `CREATION_UNPROVEN` 全是这一形态；它出现在未解决项里，也计入 `RESOURCES_RESOLVED`，而不是被判成“干净”。

`WRITE_OUTCOME_UNKNOWN` 的写永不重放：`replay_allowed` 恒为 `False`，回归用例覆盖超时、断连与清理失败三条路径。本轮 26 轮真实运行中重放次数为 0。

## 5. FIXED 与 ADAPTIVE

两种模式共用同一个 Deep Agents 运行时、同一套 Policy/Validator/Executor、同一份批准策略，只改预算的来路：

- `FIXED`：完全使用历史数字（16 次模型、30 次 HTTP、420 秒、每任务 28,192 Token 信封），可复现 P3-A.1，作为 A/B 基线。
- `ADAPTIVE`（产品默认）：以历史数字为基数，按估算与天花板执行；有进展就按增量增长（模型调用 +4、Token +60k、时间 +120 秒且保留 30 秒清理预留），HTTP 不变；无进展连续 3 次即停。

安全边界在两种模式下都不变，并且比“可调预算”更强：

- 业务 HTTP 只来自操作员授权（`target.max_requests`），运行时**只能使用、不能扩大**；估算超出授权时发 `HTTP_AUTHORITY_INSUFFICIENT` 结构化诊断并等待授权。
- 绝对上限：96 次模型调用、400 次请求、3,600 秒。
- 危险操作仍需人工授权；未授权的请求在策略层被拒。
- 清理预留（2 次请求 / 30 秒）在时间增长时不被吃掉。

机制行为的诊断样例（**不同源码冻结，不作为验收数据**，仅说明增长链路真的被走到）：

- `runs/p3a2/diag-6`：授权 40 次请求、估算 41，`HTTP_AUTHORITY_INSUFFICIENT` 写明“需要 41、已授权 40、30 项义务”，运行时没有自行放宽权限，仍按 40 授权完成。
- `runs/p3a2/final-prev/A/prerelease-adaptive-r1`（较早源码）：同一上线前目标连续 9 次增长，发出 51 次业务请求、覆盖 20/31 项义务、用掉 68 次模型调用与 560k Token；同源的 FIXED 轮次为 16 次调用、0 次请求、0/31。

也就是说：**增长确实能把“被上限掐死”的轮次往前推**，代价是 Token 与请求量成倍增加，而且清理凭据必须同步跟上（该轮 22 个资源仅“删除回执、无回读”，因此判 `CLEANUP_UNPROVEN`）。

## 6. 独立真实模型结果

冻结样本分两批，均未参与调优，源码冻结指纹 `4194c7f663059e2b`（`src/agenttest` 全量哈希），全部串行、各自独立靶场：

- **Batch A（同口径复现）**：P3-A.1 的四条原始目标文本，FIXED 与 ADAPTIVE 各跑一次。
- **Batch B（独立冻结样本）**：六个互不相同的目标，只跑 ADAPTIVE，每目标 3 次：CRUD 功能、删除后状态、接口故障调查、上线前、参数边界/负向、真正模糊的自然语言。任务文本里没有策略 ID、步骤或断言，任何一轮都不按任务名特判。

判定口径（先定义，再看数）：

- **严格完成**：`agenttest.task-completion.v1` 的 `complete`，由确定性判据计算，模型的收尾陈述不参与判定。
- **选中范围完成 / 批准范围覆盖**：本轮选中范围内有执行证据的义务比例，以及同样证据对全部已批准义务的比例；两者同时公布。
- **清理**：`write_effects` 六态逐项计数，只有 `CREATED_AND_CLEANED` 算已解决。
- **成本**：模型调用与 Token 取 `summary.budget.ledger`（授权总账，含 Focus、设计与 Agent 循环），HTTP 取传输层尝试次数。

## 7. 与 P3-A.1 同口径对比

## 8. Token、HTTP、时间与严格完成

- **总量**：26 轮、8 轮严格完成（31%）。模型调用 217 次、Token 1,675,573、业务 HTTP 96 次、工具调用 190 次、墙钟 1,203.5 秒。用量未知 0 轮。

## 9. 安全与清理

26 轮真实运行的清理账本：

- `CREATED_AND_CLEANED` 23 个资源；`CREATION_UNPROVEN` 12 个（全部是被拒集合 POST、没有批准回读）；`CLEANUP_UNPROVEN` 5 个（删除回执但没有该用例的回读）；`CREATED_CLEANUP_FAILED` 0 个；`WRITE_OUTCOME_UNKNOWN` 0 个。
- **未知写重放 0 次**；没有任何一轮发出未批准的业务请求；目录靶场（`allow_mutations=False`）的写操作没有产生任何 HTTP 记录。
- 误报 5 轮（把靶场常态 503 之外的现象判成异常），漏报 23 轮——绝大多数漏报是那些零请求的轮次：没有观测就没有异常判定，报告如实记为未覆盖，而不是“未发现异常”。

安全边界逐项：

- **业务 HTTP 权限只来自操作员**：`resolve_plan` 把 `http_requests` 固定为 `target.max_requests`，ADAPTIVE 的估算只影响“够不够”的诊断；`ExecutionState.extend` 对 `http_requests` 直接返回 `False`（回归用例断言）。
- **绝对上限**：96 次模型调用 / 400 次请求 / 3,600 秒。
- **无进展停止**：确定性签名（证据集合、清理回执、计划指纹、未解决阻塞、待确认项），连续 3 次无变化即 `NO_PROGRESS`，本轮真实触发 2 次（调查与上线前各一次），均写入报告。
- **未知写不重放**：`replay_allowed=False` 恒成立。
- **清理预留**：仍有未释放资源时保留 2 次请求与 30 秒，时间增长不能吃掉它。
- **危险操作人工授权**：批准策略与授权过滤未改。
- **未授权请求拒绝**：`directory` 靶场的写操作在策略层被拒，模型无法绕过。

## 11. 未解决问题

1. **422 的副作用在冻结靶场里仍无法证明。** 靶场没有集合列表读，也没有为“被拒集合 POST”批准缺失读，按本轮规则只能保留 `CREATION_UNPROVEN`（边界目标 r3 的 12 条即此形态）。要变成 `NO_SIDE_EFFECT_PROVEN`，必须在批准目录里补一条针对该资源的读。
2. **上线前 31 项义务仍难以在单轮内测完。** 最好的一轮 8/31，ADAPTIVE 在更早的诊断运行里到过 20/31 但耗费 68 次调用、51 次请求、560k Token，并留下 22 个只有删除回执的资源。瓶颈是“一轮承担 31 项义务”的计划粒度，不是预算数字。
3. **清理收尾缺少跨用例凭据规则。** 5 个 `CLEANUP_UNPROVEN` 都是“删除确实执行过、但该用例没有批准回读”。是否允许把同一资源的其他用例回读作为清理凭据，是策略决定，本轮保守判为未证明。
4. **零请求轮次仍占多数**（26 轮中 11 轮 0 次业务请求）。原因分散在：Focus 授权冲突类拒绝（不重试）、构造阶段 `CONSTRUCTION_ORDER_INSTANCE_CONFLICT`、Agent 循环自行收尾、真正需要澄清。范围账本与停止理由都能定位到具体原因，但没有一条能把“零请求”直接变成“有证据”。
5. **预算分两层。** 运行级 `ExecutionBudget` 与项目级 `SuiteLedger` 各自记账；ADAPTIVE 只增长前者，所以出现过“运行级还有余量、被 `SUITE_MODEL_BUDGET_EXHAUSTED` 拒绝”的轮次（较早诊断源码）。两者需要统一口径或由操作员一次批准同时抬高。
6. **增长判据偏宽。** “新证据”不等于“接近完成”，调查/上线前目标会持续增长；应改为“未闭合义务减少”或“阻塞解除/清理完成”。
7. **FIXED 臂的严格完成不稳定**（同一文本 2/4–3/4 之间跳动），单轮 A/B 不足以做机制归因；Batch A 应至少 3 次重复。
8. **范围外未做**：Durable Resume/Checkpoint、正式 HITL、Langfuse 观测、AG-UI/A2A。Web/CLI/Suite 入口本轮没有重跑真实模型，只由离线套件覆盖。

## 12. P3-B 进入条件

1. **清理收尾有明确策略**：未证明资源要么由运行时用已批准删除收尾，要么明确“跨用例回读复用”的判定规则，二者都要有确定性回归。
