# AgentTest：简历与面试材料

定位：面向隔离测试环境的可审计 API 测试与回归平台。技术栈 Python、FastAPI、LangGraph、Pydantic、HTTPX、MCP、pytest、React/TypeScript、GitHub Actions。

## 本轮可用简历条目与边界

- 构建基于公开观测的只读反馈决策与确定性证据核验，在两业务域建立12题、三轮、三组冻结对照，分别统计证据获取、严格结论和正确弃权；发现候选结论增益伴随弃权退步，保留全部失败及逐调用用量，未将模型提案直接采信为结论。

本轮已验证的是受控机制与可复核实验，不写“模型定位准确率提升至通用水平”或“节省人工时间”。
[完整结果](evidence-value-report.md)：A19/36、B29/36、C36/36；B正确弃权5/12低于A9/12，
端到端1/6。下列原三条与旧案例保留各自来源和阶段，不与新分母混算。

## 简历三条

- 实现自然语言目标到 API 测试计划的受控执行链，使用 Pydantic DSL、OpenAPI、Policy 与 Intent 校验约束操作、角色及资源引用，确定性执行器管理凭据、跨接口 ID 和断言；未经授权的计划在业务请求前拒绝，不执行模型生成的代码。
- 基于 LangGraph 实现失败反馈决策闭环，模型在批准能力中选择只读调查或停止；单次运行限制两次调查、四次模型请求，记录证据引用及 Token，并保留原业务判定。通过 24 题三轮开发对照保留故障、拒绝、漏诊与逐次用量，不将工具成功当作结论正确。
- 提供待审配置草稿、本地脱敏追踪和无模型 pytest 回归导出；在课程、工单两域验证新增任务复用 4 份核心输入中的 3 份，自动带入 3 个配置摘要。维护 Windows/Linux × base/agent CI；开发评测与独立人工留出评测分别标注。

数字来源：[反馈结果](demo-evidence/feedback-typed-live-summary.json)、[接入复用计数](demo-evidence/onboarding-summary.json)。两个分数仅是小样本开发验证，不能写成通用准确率。回归包导出还需要完整通过的报告与操作员批准，不将失败调查结论转为 PASS 回归包。

## 案例一：模型生成合法 JSON，却绑定错资源

问题：跨接口测试必须把创建结果中的资源标识传给读取接口，模型容易把完整响应、嵌套字段或数组位置混用。

失败场景：根响应本身是 ID 时，模型仍追加属性名；另一次模型把 name 的字符串包成对象。前者在 selector 策略分支拒绝，后者是 OPENAPI_VALUE_TYPE，均没有业务请求。

方案：从可信契约和策略派生引用候选、字段类型及允许参数槽位，补充固定诊断分支和数字位置；合法根响应 `$` 的含义只在存在相应绑定的上下文中说明。

替代方案取舍：只加提示无法成为安全边界；放宽执行校验或修改断言会让错误计划进入系统。为所有场景增加说明还会挤占小请求预算，因此只按存在的能力提供说明。

实现：generic_arguments.py 与 generic_references.py 在模型 Schema 和本地验证两处约束；原 Policy、Intent、OpenAPI 检查继续有效。

验证与边界：新根响应任务 9/9，原诊断批次根响应 0/3、原 FC 类型错误仍保留。不能因为新题通过就重写旧成绩，也不能宣称任意引用语义均支持。

## 案例二：测试失败后，怎样让模型调查而不越权

问题：原始断言失败说明现象，未必足以支持进一步结论。

失败场景：禁止跨账号读取的请求返回成功；需要所有者读取同一资源，核对它确实是有效资源。另一例是字段回读不一致，需要同角色再读确认重复出现。

方案：把调查工具当作操作员批准的固定菜单。模型选择菜单项或结束，执行器校验角色、源资源引用及剩余预算，再使用原活跃会话执行 GET；新的证据交回模型，最后由确定性规则核对结论。

替代方案取舍：模型任意 HTTP 工具会绕开授权；失败后重放写操作会污染状态；让模型直接判断 PASS 会混淆断言与推测。本实现只允许有界只读反馈，不自动修复或改写测试。

实现：feedback_runtime.py 的 decide/validate/execute/close LangGraph；FeedbackAction 严格结构、不可变授权快照、重复调查键、独立 FeedbackResult、逐调用统计和超时/取消落盘。

验证与边界：覆盖无效工具/参数、重复、预算、超时、工具错误、未知用量及证据不足。真实三题业务正确 3/3、调查结论 2/3：第三题证据已足够但模型仍弃权，属于漏诊；工具执行成功不能算定位成功。结论只支持访问边界或重复回读症状，无法证明数据库或业务实现的根因。

## 案例三：复用配置与回归，收益如何证明

问题：契约能说明请求结构，无法替操作员决定角色权限、业务预期和资源关系。每题手工复制已有配置也容易漂移。

失败场景：把 OpenAPI 自动发现的候选当作批准策略，会把“接口存在”误解成“可以执行且预期正确”。只展示一次成功运行，也不能证明后续维护成本下降。

方案：项目草稿只提取确定性结构并列出五类待审项；新增任务复用已检查的项目配置、自动计算三个摘要，保留任务约束人工填写。草稿使用不同 Schema 且授权恒为 false。完整通过的批准场景由固定模板导出 pytest，以后回归不再调用模型。

替代方案取舍：没有实际计时便不声称节约工时；不引入向量库、队列或外部观测平台来证明不存在的瓶颈。

实现：onboarding.py 复用 discovery/check-project；local_trace.py 从脱敏报告关联五阶段；regression.py 使用固定 Python 模板、JSON 数据及摘要核对。

验证与边界：两域每次新增任务只改任务文件两个叶值，4 份核心输入复用 3 份。首次五类与后续三类待审项范围不同，不计算简单下降百分比。实际人工维护时间、独立留出成绩与任意项目接入收益未知。

## 面试追问

### 本轮案例：证据到手为什么仍不能得出结论

问题：旧封印20/21取得有效支持证据，严格结论却只有11/24。工具成功不等于模型结论正确。

失败场景：9次有证据明确弃权；新候选也会在HTTP检查失败、异操作或没有重复字段失败时，
仅凭表面相似选择持续回读症状。自然语言确认中还出现结论名称正确但引用错误角色证据。

方案：从已批准绑定和当前检查派生资源/角色/字段关系，枚举完整动作组合，保留合法枚举提案诊断；
最后仍由原Executor和确定性支持检查决定采信。另加入不读标签的固定调查规则，复用同一执行入口。

替代方案取舍：不增加工具预算、不改断言、不让模型查看评分器或答案，也不通过补跑追求好成绩。
不能用引擎拒绝猜测后的NEEDS_REVIEW冒充模型主动正确弃权。

实现：evidence_context.py、evidence_control.py及原feedback_runtime；评分与封印在
evidence_evaluation.py，补充只读归因evidence_attribution.py区分确认断言和未知拒绝。

验证与边界：12题三轮每组36位置，B支持类24/24优于A10/24，但弃权5/12低于A9/12，
C36/36且零模型；自然语言端到端仅1/6。结论是这两条公开规则更适合确定性完成，模型仅作为
受控规划/建议来源，本轮没有证明额外可靠性或人工节时。正式独立人审尚未完成。

为什么需要模型：适合在明确支持范围内把目标组织成跨接口计划，并基于反馈从有限工具中选择下一步；执行和稳定回归无需模型。

与普通 pytest 的关系：固定 pytest 更便宜、更稳定，适合确定需求长期回归；Agent 的候选收益是减少新目标编排和证据整理工作，但需要配置与模型成本，尚未取得独立人工节时证据。查看配对开发报告中的完整失败与分母，不能预设 Agent 必须胜过 pytest。

为什么不使用 RAG/多 Agent：当前缺口在参数、资源引用、可核查调查及证据管理，已有可信配置能表达；新组件不能替代授权和断言，也未被本 Goal 授权。

可以生产使用吗：当前是隔离环境工具与本地只读控制台，缺少生产多租户审批和部署认证。目标必须显式授权，不向生产开放任意 URL 或模型代码执行。

完整 24 题三轮开发比较见 [价值与成本报告](goal-value-report.md)。不要仅引用三题 FE 小样本而省略完整评估中的拒绝、漏诊和模型结构失败；固定 pytest 本轮更稳定。
