## 离线验证

先建立三个任务服务反例，使用确定性模型响应和内存 HTTP 目标。修复前分别复现多余匿名请求、下游读取误暂停和 UNKNOWN_FIELD 全局拒绝。保留[数据与受阻输入首次失败](evidence/mixed-planning-p0-20261107/red.xml)、[无参数接口的权限越界失败](evidence/mixed-planning-p0-20261107/red-permission.xml)。最初权限夹具额外携带路径参数，先触发既有身份输入校验；随后改成与故障相同的无参数公开接口，才准确复现多余请求。

新增 [34 项测试](../tests/test_mixed_planning_p0.py)，包括：

- 权限待审被模型标为 required 或 needs_review，两者均不执行匿名兜底，独立读取继续。
- 另一个分项明确要求匿名读取同一接口时正常执行；同分项明确匿名动作也可保留，其他身份不能借用。
- 忽略生成约束的模型仍被最终计划门禁拒绝，不将 reviewer 改成匿名角色。
- 合法跨接口来源实际用于下一次请求；同一字段另作已批准断言时，来源与断言分别有执行证据。
- 未批准选择器、未知断言、错误生产者、错误角色和错误实际绑定受到限制，原方案不被改写。
- 受阻参数保留操作、字段、原值和原文偏移；错误来源、字段歧义、缺少不可用证据继续拒绝。
- 权限待审与明确重复读取、严格顺序混合时，漏读、错序、错误身份仍触发原门禁。

## 仍然存在的限制

1. 来源识别是有边界的语法提取，只确认相邻、单一映射的生产者和消费者。较远指代、多生产者、隐含参数等复杂语义仍可能待审或拒绝。JSONPath 不因出现于原文而获得批准。
2. 同一分项同时引用数据并隐含检查该字段时，无法证明谓词或检查对象就继续待审。明确分项的批准断言与数据用途已分别验证。
3. 不可用输入的确定性待审关联目前覆盖路径和查询字段。请求体嵌套字段或歧义操作没有新增豁免。
4. 反向测试发现原有次数提取器不能独立识别“匿名连续读取两次……”这一前缀形式；修复前后的提取函数相同。本轮未扩展该语法。最终顺序测试使用原有支持的“连续读取两次……（匿名）”，原先暴露边界的测试结果继续保留。该限制意味着不能保证任意复合语句的次数分母完整。
5. 违反 Schema 的错误资源、身份或断言方案仍可能使同组合法工作一并拒绝；本轮没有自动拆解或修复被拒方案。没有重新运行真实模型，因此性能、成本及模型输出分布影响未知。
